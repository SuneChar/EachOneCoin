# 局域网扫码联机：Windows 防火墙排查记录

## 现象和定位

一次 Windows Unity Editor 作为房主、Android 手机扫码加入的联调中，二维码能引导客户端开始连接，但 Android 的 Mirror/KCP 日志报告约 10 秒连接超时。检查发现：

1. 电脑与手机在同一 IPv4 网段；电脑能够 ping 通手机。手机 ping 电脑失败，但这本身不能证明 UDP 也被阻止，因为 ICMP 可以单独被防火墙过滤。
2. 电脑房主进程正在 `0.0.0.0:7777` 监听 UDP，Unity Editor 中没有对应连接错误；房主没有收到手机连接。
3. 当前 WLAN 被 Windows 归类为公用网络。防火墙存在一条针对该 Unity Editor 可执行文件的公用网络入站**阻止**规则，覆盖所有协议和端口。
4. 经用户授权，临时禁用该阻止规则，并仅允许该手机的 IP 访问 Editor 的 UDP 7777。手机随后连接成功、通过房间认证并获得玩家席位。测试结束后临时规则删除、原阻止规则恢复。

因此，这次故障有充分证据指向房主电脑的防火墙规则。不能据此推断所有扫码超时都由防火墙引起：错误网卡、客户端隔离、端口不一致及手机系统限制等也应分别排查。**单纯更换 UDP 端口不能绕过针对该程序所有端口的明确阻止规则。**

## 建议排查步骤

1. 确认双方在允许设备互访的同一局域网。房主有多个网卡时，在房间界面切换地址，选择客户端可达的网卡地址；二维码只传地址和端口，不建立中继。
2. 确认房主已创建房间，并核对二维码显示的地址与 KCP 端口。Windows 可用 `ipconfig` 查网卡地址、`netstat -ano -p udp` 查监听端口及进程 ID。默认端口为 UDP 7777，具体以运行时 KCP 配置为准。
3. 查看客户端状态和日志。连接超时表示连接未建立，并不能单独证明扫码内容、认证或防火墙中的某一项必然出错。Android 开启 USB 调试后，可通过 `adb logcat -s Unity AndroidRuntime` 观察 Unity 日志。
4. 核对房主进程的 Windows 防火墙入站规则和当前网络类别。明确的阻止规则可能覆盖新增的允许规则；不要只看是否存在端口允许规则。必要时由设备管理员批准后做**短时、限定来源与端口**的对照测试，结束后恢复原规则。
5. 无法修改电脑入站规则时，可尝试手机当房主、电脑主动加入；是否可用仍取决于手机和局域网环境。

## 本次长期配置和安全边界

用户随后授权将测试电脑的当前 WLAN 设为专用网络，新增一条仅针对当前 Unity Editor 程序、专用网络、本地子网、入站 UDP 7777 的允许规则；原公用网络阻止规则保持启用。该配置是**本机系统设置，不随 Git 同步**，不同 Unity 版本、安装路径、Windows 构建或实际端口可能需要各自检查。改变网络类别会影响系统对该网络应用的其他专用网络策略，应只对可信网络操作；不要为了调试关闭整个防火墙。

长期规则和网络类别已核实生效；在此记录时，尚未观察到长期规则生效后的第二次手机扫码连接，因此该次连接结果未验证。此前临时放行实验中的认证成功是独立的已验证结果。

## 平台验证状态

二维码编码和解码的编辑器内往返检查通过，且曾在房主编辑器中实际显示二维码；Android 客户端在临时放行实验中成功认证。Android 打包、摄像头权限流程和 Keystore 重连跨进程持久化仍需在目标设备及构建上单独复测。Android 最低版本为 API 23。
